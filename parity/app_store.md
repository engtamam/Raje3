# متجر التطبيقات + تطبيقاتي + السلة + السعة — الكونسول مقابل الجوال

**الحالة:** دراسة كاملة من الكود الحقيقي — كل ملف كونسول ذو علاقة قُرئ سطرًا سطرًا (لا تلخيص إيجنت)،
وكل مسار خادم ذُكر هنا تأكّدت منه مباشرة من `services/operations/app/user_actions.py` و
`platform/services/billing-service/app/user_actions.py`. البناء بالجوال لم يبدأ بعد — هذا checklist
مرجعي قبل البدء، ليس تقرير إنجاز.

**القاعدة الأمنية المؤكَّدة:** السعر **لا يُرسَل أبدًا من العميل** — السيرفر يقرأ الباقة من قائمة
الأسعار عنده ويحسب السعر النهائي بنفسه (`billing_service.py::_compute_renewal`). العميل يرسل فقط
`plan_id`/`interval`/`quantity`/`coupon_code`/`payment_token`. البطاقة تُرسَل مباشرة من المتصفح
لشركة الدفع (ميسر) عبر مفتاح عام (publishable key) — لا تمر على سيرفرنا إطلاقًا. الجوال يطبّق نفس
المبدأ حرفيًا: صفر منطق مالي بالتطبيق، بس واجهة تطلب من نفس الأبواب.

## 1) سجل التطبيقات (`apps/console/src/apps.ts`, `APP_ROWS`)

مصدر واحد لكل تطبيق مُباع — 13 تطبيق حقيقي + السعة (إضافة كمية، ليست تطبيقًا). كل صف يحمل:
`id`, مفتاح الصلاحية (`feature.xxx` أو `null` للأساس), الاسم, جملة تسويقية واحدة, القسم اللي
يفتحه (أو `openPath` لو ما له قسم), أيقونة/لون للبطاقة الصغيرة.

| # | id | الاسم | القسم/الفتح | ملاحظة |
|---|---|---|---|---|
| 1 | campaigns | الحملات | messages | |
| 2 | loyalty | برنامج النقاط | points | |
| 3 | bookings | الحجوزات | bookings | |
| 4 | insights | صفقات | داخل «محلّي» (بدون شاشة خاصة) | `openPath: /shop` |
| 5 | rating | التقييم | rating | ميزاته تجي مباشرة مع قراءة الملكية (لا نداء منفصل) |
| 6 | contacts | جهات الاتصال | customers | **مجاني** لكل محل من أول يوم، دائمًا مملوك |
| 7 | visit | تسجيل زيارة | — (يُباع مستقل) | ميزاته inline مثل rating/contacts |
| 8 | whatsapp | المساعد الذكي عبر واتساب | `/whatsapp-assistant` | البطاقة الذهبية VIP الوحيدة بالمتجر |
| 9 | partner-loyalty | ولاء الشركاء | داخل «محلّي» | خصم على اشتراكك أنت عند محل آخر يجدد |
| 10 | referral-partnership | شراكة استراتيجية | referral-partnership | **مبنية بالجوال فعلاً 2026-09-23** — راجع [referral.md](referral.md) |
| 11 | mobile-ai-assistant | المساعد الذكي (تطبيق الجوال) | `/account` (fallback صادق) | **لا شاشة كونسول له إطلاقًا ولن تكون** — سطحه الوحيد الجوال، سعره صفر عمدًا |

| — | (لا id) | زيادة السعة (موظفين/فروع) | داخل «كل التطبيقات» فقط | إضافة كمية على اشتراك موجود، ليست تطبيقًا مستقلاً |

**للجوال:** 9 من الـ13 غير مبنية بالجوال أصلاً كشاشات (campaigns/loyalty قسمين موجودين فعليًا لكن
بأسماء ثانية — تأكد قبل الافتراض)، وهذا مو مجال هذا الملف — مجاله فقط "المتجر نفسه": القائمة،
البطاقة، التفاصيل، السلة، الدفع، السعة. أي تطبيق ما له شاشة جوال بعد يظهر بالمتجر "مقفول" فقط، لا
تُبنى شاشته هنا.

## 2) شاشتان مختلفتان تمامًا من نفس البيانات (`launcherCatalog.ts`)

| | «تطبيقاتي» (`myApps`) | «كل التطبيقات/المتجر» (`allApps`) |
|---|---|---|
| **مين يشوفها** | كل الأدوار | فقط من يملك صلاحية `operations.create_operator` (المالك والمدير) |
| **وش تعرض** | فقط اللي هذا الدور يقدر يفتحه أصلاً (نفس منطق الشريط الجانبي) | كل التطبيقات، حتى المقفولة |
| **فيها سعر/شراء؟** | **لا — تصفّح بحت، ما فيها لا سعر ولا زر شراء ولا نافذة تفاصيل** | نعم — كل شي: سعر، خصم، اشتراك، إلغاء |
| **فيها سلة؟** | لا | نعم |
| **فيها سعة (موظفين/فروع)؟** | لا | نعم |

**قرار حاسم للجوال:** لازم شاشتين منفصلتين فعليًا بنفس المنطق — «تطبيقاتي» بسيطة صفر بيانات مالية،
و«المتجر» فيها كل آلية الشراء. دمجهما بشاشة وحدة بفلتر يخالف تصميم الكونسول الأصلي.

## 3) البطاقة نفسها (`AppTile.tsx` + `AppDetailsModal.tsx`)

- **ثلاث ضغطات منفصلة** على نفس البطاقة: (أ) الضغط على البطاقة نفسها = يفتح التطبيق مباشرة،
  (ب) زر «التفاصيل» = يفتح نافذة منبثقة فيها كل شي (لا يفتح التطبيق)، (ج) زر «أضِف» = يضيف/يشيل
  من السلة بدون ما يفتح أي شي. الثلاثة لازم تشتغل بدون ما تتعارض مع بعض.
- شارة أعلى البطاقة: إما "مقفول" (رمادي) أو "نشط"/"تجريبي" (أخضر) — **غياب الشارة يعني تطبيق مجاني
  بلا اشتراك أصلاً** (مثل صفقات/الأساس).
- نافذة التفاصيل: عرض مميزات حقيقية بشكل بطاقات متحركة (staggered animation)، مو قائمة نقطية عادية
  — بيانات المميزات نفسها إما جاهزة مسبقًا (rating/contacts/visit) أو تُجلب بنداء واحد وقت الفتح.
- **البطاقة الذهبية (VIP)**: تطبيق واحد بس (المساعد الذكي عبر واتساب) — خلفية ذهبية متدرجة، شريط
  "VIP" بالزاوية، وميض لامع متحرك بشكل دوري. هوية ثابتة بالكود، مو بيانات.
- شريط سعر مختصر يبان على وجه البطاقة نفسها (بدون فتح التفاصيل): السعر، خصم إن وجد، رقائق
  "وحدات ذكاء اصطناعي مشمولة" إن وجدت — **يجب أن يكون مطابقًا تمامًا لما يبان داخل نافذة التفاصيل**،
  رقم واحد لا رقمين مختلفين.

## 4) السلة (`useAppBilling.ts` + `CartBar.tsx`)

- السلة نفسها: مجرد قائمة IDs بذاكرة الجهاز (React state) — **لا يوجد حفظ بالسيرفر قبل الدفع**،
  تختفي لو أغلق الصفحة.
- **إضافة تبعية تلقائية**: تطبيق زي "برنامج النقاط" يحتاج "تسجيل زيارة" أو "الحجوزات" أولاً — لو
  ضاف المحل النقاط بدون ما يملك أحدهما، السلة تضيف التطبيق المطلوب تلقائيًا معه (مو رسالة نصية
  بس)، مع إشعار صريح "أُضيف X تلقائيًا لأن Y يحتاجه".
- **السعر الحقيقي يُطلب من السيرفر عند كل تغيير بالسلة** (تأخير 200ms عشان ما يرسل طلب كل ضغطة)،
  ويُستبدل به أي مجموع محسوب محليًا فور وصوله. المجموع المحلي (جمع الأسعار المعلنة) يُعرض فقط
  كحل مؤقت أثناء انتظار جواب السيرفر، مع توضيح إنه "بدون خصم أو ضريبة".
- السلة تعرض: عدد العناصر، أسماء التطبيقات، المجموع، تفصيل (سعر فرعي/خصم/ضريبة/الإجمالي النهائي —
  كل سطر من هذي مباشرة من جواب السيرفر، صفر حساب محلي)، وزر إزالة لكل عنصر.
- زر "إتمام الشراء" يفتح نموذج البطاقة، ونفس مسار الدفع أدناه.

## 5) الدفع (`payment.ts`)

- بوابة الدفع: **ميسر (Moyasar)**. البطاقة تُرسَل مباشرة من المتصفح لميسر بمفتاح عام — سيرفرنا ما
  يشوف رقم البطاقة إطلاقًا، بس يستلم "توكن" لمرة واحدة بعد ما ميسر يتحقق منها.
- **كل عملية تفعيل بطاقة تمر بخطوة تحقق إضافية (3D Secure) تقريبًا دائمًا** — المتصفح ينتقل فعليًا
  لصفحة البنك ويرجع. بالجوال هذا يعني **WebView داخلي**، مو تبديل صفحة متصفح عادي.
  - عند الرجوع من التحقق، لازم نتأكد من حالة التوكن فعليًا (مو نثق بالرابط المرجع وحده) قبل
    استخدامه — نفس الانضباط المطبَّق بالكونسول (`confirmToken`).
- كل خطأ حقيقي (رفض البنك، تعذّر الاتصال، بطاقة مرفوضة) له جملة عربية مختلفة، ما فيه رسالة عامة
  واحدة لكل الحالات.

## 6) السعة — موظفين/فروع (`billingShared.tsx::CapacityAddonCard`)

- ليست تطبيقًا — إضافة كمية على اشتراك قائم، تظهر **فقط** داخل «كل التطبيقات»، أبدًا داخل
  «تطبيقاتي» (قرار صريح من المالك).
- عداد +/- بسيط. **الوحدة الأولى تمر بمسار الشراء العادي (تحتاج بطاقة أول مرة)**، وأي وحدة بعدها
  مجرد تعديل كمية على نفس الاشتراك (رفعها يخصم الفرق فورًا، تخفيضها يُجدوَل للتجديد القادم).
- إزالة آخر وحدة = إلغاء الاشتراك بالكامل، يحتاج تأكيد صريح (نفس خطوة تأكيد الإلغاء).
- **هذا بالضبط اللي زر "زيادة السعة" الحالي بالجوال لازم يفتحه — بدل ما يطلع لموقع الكونسول.**

## 7) الرفض والإلغاء (كل الحالات الحقيقية)

- تطبيق مقفول لأنه يحتاج تطبيق ثاني أولاً (`requiresAny`) → جملة تسمّي التطبيق المطلوب بالاسم،
  ما تقول "غير متاح" بس.
- إلغاء تطبيق له تطبيقات تابعة (مثلاً إلغاء "تسجيل زيارة" ويسحب معه "الحجوزات") → تحذير صريح
  بأسماء التطبيقات التابعة قبل التأكيد النهائي.
- إلغاء = "يوقف التجديد" (الاشتراك يستمر لين نهاية الفترة المدفوعة) — له زر "تراجع" منفصل ما دام
  ما انتهت الفترة بعد.
- خصم بين تطبيقين مرتبطين: badge أخضر "خصم مطبَّق فعلاً" لو محقق شرطه، أو badge ذهبي "عرض محتمل"
  لو التطبيق الثاني غير مملوك بعد (يعني لو اشتراه بيحصل الخصم).
- عدم توفر الدفع أصلاً (لا مفتاح بوابة على السيرفر) → جملة واحدة صريحة: "الدفع بالبطاقة لم يُفعَّل
  بعد... لن تُحسب عليك أي رسوم حتى ذلك الحين" — تظهر لحظة الضغط على "اشترك"، لا قبلها كرابط ميت.

## 8) كل نداء خادم حقيقي مستخدم هنا (بالطريقة والمسار الدقيق)

| الفعل | الطريقة | المسار | ملاحظة |
|---|---|---|---|
| تصفح الباقات | GET | `/api/v1/billing/plans` | قائمة كل الباقات المعروضة |
| اشتراكاتي الحالية | GET | `/api/v1/billing/subscriptions` | |
| معاينة الخصم | GET | `/api/v1/billing/discount-preview` | خصومات مطبَّقة + محتملة |
| هل الدفع مفعّل | GET | `/api/v1/subscription/payment` | (عبر خدمة العمليات، وليس الفوترة مباشرة) |
| ملكيتي الحالية (لكل قفل بالتطبيق) | GET | `/api/v1/subscription/apps` | المصدر الوحيد لأي قفل/فتح بأي شاشة |
| تفعيل اشتراك واحد | POST | `/api/v1/subscription` | (`subscription.activate` — طريقنا نحن، يفرض ربط واتساب قبل أي دفع لتطبيق يحتاجه) |
| شراء سلة كاملة | POST | `/api/v1/subscription/checkout` | كل العناصر تُتحقق كمجموعة واحدة |
| معاينة سعر السلة | POST | `/api/v1/subscription/checkout/preview` | قراءة فقط، لا يُنشئ ولا يخصم شي |
| تجديد مبكر | POST | `/api/v1/subscription/renew-now` | |
| إيقاف تجديد تطبيق | POST | `/api/v1/billing/subscriptions/{id}/cancel` | يحتاج تأكيد |
| التراجع عن الإلغاء | POST | `/api/v1/billing/subscriptions/{id}/undo-cancel` | |
| تغيير كمية السعة | POST | `/api/v1/billing/subscriptions/{id}/change` | نفس مسار "تغيير الباقة" |
| توكينة البطاقة (مباشرة لميسر، ليس سيرفرنا) | POST | `https://api.moyasar.com/v1/tokens` | مفتاح عام فقط، لا مفتاح سري بالتطبيق أبدًا |
| تأكيد التوكينة بعد رجوع 3DS | GET | `https://api.moyasar.com/v1/tokens/{id}` | نفس المفتاح العام |

كل هذي الأبواب **موجودة وتعمل اليوم بالسيرفر** — صفر تغيير باكند مطلوب لبناء الجوال.

## 9) خلاصة: قائمة بناء الجوال (ترتيب مقترح)

- [ ] شاشة «تطبيقاتي» — تصفّح بحت، صفر بيانات مالية
- [ ] شاشة «كل التطبيقات/المتجر» — بطاقات مع شارة القفل/الملكية
- [ ] نافذة تفاصيل التطبيق (مميزات + سعر + خصم/عرض)
- [ ] السلة (حالة محلية + معاينة سعر حية من السيرفر)
- [ ] شاشة الدفع (WebView لميسر + التحقق بعد الرجوع)
- [ ] بطاقة السعة (عداد موظفين/فروع)
- [ ] استبدال رابط "زيادة السعة" الحالي (يفتح موقع الكونسول) بالشاشة الجديدة
- [ ] كل حالات الرفض السبع أعلاه، كل وحدة بجملتها العربية الخاصة

**لا شغل باكند بهذي القائمة إطلاقًا — كلها واجهة جوال فقط، تتكلم مع الأبواب الجاهزة أعلاه.**
