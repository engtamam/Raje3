## LANE 1 — DEAD WIRES

### [قاطع] Campaign dispatcher's daily_share is never supplied by the container — the spread promise is enforced nowhere
`services/campaigns/app/container.py:293`

**ما يحدث للمحل:** A shop's provider ceiling leaves the campaign a share of, say, 40 sends today (share.per_day=40, computed by HttpRoom and shown in the preview as «سنوزّعها على N أيام»). Dispatcher.fire computes `per_pass = self._daily_share or self._batch` — _daily_share is 0 because nothing ever passed it — so it sends up to DISPATCH_BATCH_SIZE=200 in one pass, five times the share, consuming the reserve that insights held back for the automatic reminder engine. The shop's own visit-confirmation and follow-up reminders then bounce off the WhatsApp ceiling for the rest of the day, and the campaign's preview sentence about spreading over days was never true.

**الدليل:** `Dispatcher.__init__` accepts `daily_share: int = 0` (core/dispatch.py:36,48) and uses it at dispatch.py:73. `grep -rn "daily_share" services/campaigns/app` returns hits ONLY inside core/dispatch.py — the construction at container.py:293-296 passes store, sender, audience_resolver, batch and telemetry, and nothing else. core/share.py's per_day is consumed only by the preview route (api/v1/campaigns.py:146). Task #271 recorded this wire as fixed; the peer (HttpRoom) was added and the preview reads it, but the dispatcher's arm was not reconnected.

**الإصلاح المقترح:** Pass the computed share into the dispatcher at fire time — the number is per-tenant and per-day, so `Dispatcher.fire` should take `daily_share` from the same `share.compute()` the preview uses, rather than a constructor value fixed at boot.

This is exactly the defect commit 09fc873 ("دورة الخدمة تأتي من كتالوج المالك") was written to close; it fixed api/internal.py and never touched main.py, so the path that handles the normal case still has the bug.

**الدليل:** main.py:93 passes service_config={} literally; container.py:300 wires Ingest with no config resolver; ingest.py:59 forwards service_config or {}; scheduling.py on_visit derives cycle/lead/follow_up/enabled solely from cfgs; scheduling.py _seen/_remember make the later catch_up a no-op (duplicate=True) for the same visit_id. Only api/internal.py:144 builds a real config via _service_config.

**الإصلاح المقترح:** Resolve the tenant's service config inside the subscriber (or inside Ingest.on_event, keyed on payload['tenant']) using the same _service_config path the tick uses, so both paths hand on_visit the shop's real cycles.

### [قاطع] operations /visits/since filters by watermark AFTER a limited read — the catch-up returns nothing once a shop passes 200 lifetime visits
`services/operations/app/api/internal.py:665`

**ما يحدث للمحل:** For a tenant, the handler reads find(VISITS, {tenant}, limit=200, sort=(created,'asc')) with no cursor — the 200 OLDEST visits — and only then applies `created > since` in Python. A shop with 250 lifetime visits has a watermark above all 200 of those rows, so `fresh` is empty, `more` is False, and catch_up returns {read:0,scheduled:0} for ever. The global bootstrap branch is worse: scan_all is ORDER BY key LIMIT 200 (postgres.py:208), i.e. the lexicographically first 200 visit rows in the whole cluster, unrelated to created — past 200 visits total, discover() also permanently returns nothing, and the watermark it does advance is the max of an arbitrary key-ordered subset. Concretely: a busy workshop's pod restarts through one operations.visit.recorded; that customer's reminder is never scheduled and never repaired, and the tick reports caught_up {read:0} while looking perfectly healthy.

**الدليل:** internal.py:652-665 — both branches read a bounded page and filter `since` afterwards; find() (postgres.py:128-165) supports only equality containment, so `since` cannot be pushed down and no `after` cursor is passed; scan_all (postgres.py:198-211) orders by key, not created; reminders/core/ingest.py catch_up breaks the batch loop as soon as `visits` is empty.

**الإصلاح المقترح:** Page the read with the datastore cursor (`after`) until rows exceed `since`, or add a range predicate so the query itself is `created > since ORDER BY created ASC LIMIT n`; for the global branch, sort/seek on created rather than key.

### [عالٍ] The event path advances the tenant watermark, so a visit the at-most-once bus dropped is permanently skipped by catch_up
`services/reminders/app/core/ingest.py:65`

**ما يحدث للمحل:** Visit A is created at t=100 and visit B at t=200 for the same shop. The pod is restarting when A is published, so only B is delivered. on_event handles B and calls _advance(tenant, 200). The next tick's catch_up(tenant) asks operations for visits with created > 200 — A is never returned, never scheduled, and that customer is never reminded, for ever. The module's own docstring says the read is "the TRUE path"; advancing it from the unreliable path defeats it. The justification in the comment ("on_visit is idempotent on the visit id") only covers re-delivery, not omission — the failure mode the bus actually has.

**الدليل:** ingest.py:63-65 advances the per-tenant watermark from the event payload's `created`; catch_up reads from that same key (_watermark(tenant or '_all')). operations returns visits strictly `created > since` (internal.py:665). The only backstop is discover()'s separate '_all' cursor, which is itself broken past 200 visits (previous finding).

**الإصلاح المقترح:** Do not advance the watermark on the event path — leave the cursor owned solely by catch_up/discover, whose advance happens only after a batch was actually read and processed.

### [عالٍ] The ladder's margin lock never engages: nothing anywhere writes first_rung_returns
`services/reminders/app/core/tick.py:712`

**ما يحدث للمحل:** A customer who comes back on the first reminder every time should be locked at rung one and never see a discount (ladder.py's stated most important rule). tick._ladder reads rule.get('first_rung_returns'), but no code path in the repo ever sets that field — Scheduler._learn writes interval_days, observations, last_visit_at, anomalies and updated, and nothing else touches the rules row. So is_locked() is always False and every marketing-consented customer receives the OFFER rung, cycle after cycle, including the ones who never needed it. The shop's margin is discounted for returns it would have got free, the returns look good in the reports, and nothing connects the two — the exact outcome the module was written to prevent.

**الدليل:** Repo-wide grep for `first_rung_returns` outside tests hits only ladder.py:93/95/99/118 and tick.py:712 — a reader and no writer. Confirmed Scheduler._learn (scheduling.py) and on_visit's cancel_kind path do not increment it; only tests/unit/test_ladder.py and test_tick.py supply the value directly, so the suite passes.

**الإصلاح المقترح:** When on_visit cancels/consumes a pending ladder for a service whose rung-one reminder was the last one sent, increment first_rung_returns on the rule row (and reset it when a later rung produced the return).
