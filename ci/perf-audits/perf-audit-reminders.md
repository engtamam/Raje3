# Performance audit — services/reminders/ (read-only, same class as ci/check_deploy_wiring.py fix)

## Finding 1 (real, high impact): `Reach.prune()` does a global, un-tenant-scoped table scan, and it is called once per tenant per tick

- `app/core/reach.py:103-117` (`Reach.prune`) calls `await self._s.scan_all(REACHED, limit)` (line 111) — `scan_all` reads up to `limit` (default 5000) rows from the **entire `reached_24h` collection across every tenant**, with no `tenant` filter. Contrast this with `Reach.count()` two methods above it (`reach.py:81-86`), which correctly scopes with `find(REACHED, {"tenant": tenant}, ...)`.
- `app/core/tick.py:278-279`:
  ```
  if due:
      await self._reach.prune(now=now)
  ```
  This runs inside `Tick.run()`, which itself is called **once per tenant, per tick invocation** — see `app/api/internal.py:167-200`:
  ```
  for tenant in tenants[:s.TICK_MAX_TENANTS]:
      ...
      res = await c.tick.run(tenant, now=now, ...)
  ```
  `TICK_MAX_TENANTS` defaults to 200 (`app/config.py:352`).
- **Why this is slow, concretely**: every tenant that has at least one due row in this tick triggers a fresh, unscoped scan of up to 5000 rows drawn from *every* tenant's reach records, then loops row-by-row in Python (`for row in rows or []: ... await self._s.delete(...)`) issuing one `delete` store call per stale row found. With up to 200 tenants active in a single tick and each one having due work, that is up to 200 × 5000 = 1,000,000 row reads per tick invocation for a maintenance operation that only needs to happen once globally, not once per tenant. On Postgres this is 200 separate `scan_all` round-trips each pulling up to 5000 rows (`postgres.py` `scan_all`: `SELECT value FROM kv_store WHERE collection=$1 ORDER BY key LIMIT $2` — no tenant predicate, so it can't use the tenant-scoped GIN index at all, just a key-ordered LIMIT scan) — the exact "re-walk the same tree multiple times across different functions when the result could be computed once and reused" pattern named in the task, except here it's the *same* function re-walking the *same* global collection once per tenant in a single logical pass.
- Every tenant after the first one in a given tick does this scan for a table that the first tenant likely already pruned down (rows physically deleted), so most of the 200 calls degrade toward "scan close to N leftover rows and find nothing new to delete" — pure waste, not correctness risk, but it is 200x the necessary I/O for a job that is inherently global and idempotent within a tick.
- **Fix I would make**: either (a) scope `prune()` by tenant exactly like `count()` already does (`find(REACHED, {"tenant": tenant}, limit=..., sort=("at","asc"))`, pruning only that tenant's stale rows), which turns 200 unscoped 5000-row scans into 200 indexed, tenant-narrow reads; or better, (b) hoist the prune call out of the per-tenant loop entirely — it is genuinely tenant-independent global housekeeping ("what has aged out" across the whole reach table), so it should run once per tick invocation (e.g. once in `app/api/internal.py` before/after the `for tenant in tenants:` loop) rather than once per tenant inside `Tick.run()`. Either fix removes the ~200x redundant full-collection scan.

## Areas checked and found NOT to be a problem (no padding — reporting explicitly)

- **`app/core/tick.py` per-row loop (`_one`, lines 305-989)**: does several `await self._store`-backed calls per due row (`_prefs.get`, `_eng.get`, `_log.since`, `_consent.state`, `_sched.pending_for_subject`, `CustomTemplateStore.get`). This looks N+1-shaped but is the intended/necessary shape — each call is a single indexed `get`/`find` keyed to that one subject, `due()` itself is already a single tenant-scoped, indexed, limited batch read (`app/core/stores.py:78-109`), and the whole design (see the file's own extensive docstrings) is deliberately built around "read once per tenant, not once per row" for everything that CAN be shared across rows (the approved-templates set, the ceiling/room, the reach count — all read once in `Tick.run` at `tick.py:275-298`, not inside the per-row loop). This is not the same class of defect as an unindexed scan or a redundant full-collection walk.
- **`app/core/merge.py` (`plan`)**: sorts and loops over `pending`, which is one customer's own pending rows (bounded to `limit=200` by `ScheduleStore.pending_for_subject`, `stores.py:73-76`, realistically single digits). Pure function, no store I/O inside the loop. Not a real bottleneck at any plausible scale.
- **`app/adapters/datastore/postgres.py` `find`/`scan_all`**: already correctly indexed (GIN containment index for equality `where` filters, a matching btree for the `(collection, created DESC, key DESC)` keyset order) — the file's own comments document a prior, already-fixed instance of exactly this class of bug (mismatched ORDER BY expression defeating the index: "Bitmap Heap Scan, 5000 rows, 3.44ms" vs "Index Scan, 0.92ms"). Nothing further to flag here.
- **`ci/check_licenses.py`** and **`ci/security_gate.py`**: no per-character or per-file-content Python loops over large text, and no `rglob`/`os.walk` over the repo tree. `check_licenses.py` iterates `importlib.metadata.distributions()` (bounded to the installed dependency count, a few hundred at most) and does small string `in`/`upper()` checks on short license-classifier strings — not the "137M ord() calls" shape. `security_gate.py` only shells out to external scanners (bandit, trivy, pip-audit, detect-secrets) with path excludes already passed as CLI flags; it does no Python-side tree walking or per-character work itself.
- **`app/adapters/datastore/memory.py`**: in-memory test/dev driver; its `find`/`scan_all` are O(collection size) Python loops, but this backend is not the production datastore (Postgres is) and the collections it holds in tests/dev are trivially small — not a production bottleneck.
- **All the `for c in <collection>` per-character-looking loops found by grep** (`app/api/authz.py`, `app/api/v1/prefs.py`, `app/security/checks.py`, `ci/check_licenses.py`) iterate small, fixed-size collections (permission-capability sets, the 5-6 `CLASSES` labels, license classifier tokens) — none of them scan per-character over arbitrarily large text the way the fixed CI gate did. No regex-vs-loop win available here.

## Bottom line

One real, well-defined finding: `Reach.prune()` (`app/core/reach.py:103-117`) is an unscoped, whole-collection scan that `Tick.run()` calls once per tenant per tick (`app/core/tick.py:278-279`, driven by `app/api/internal.py:167-200`, up to `TICK_MAX_TENANTS=200` per invocation) — the same collection gets rescanned in full up to 200 times in a single tick sweep for a job that is tenant-independent and only needs to run once. Fix: scope the query by tenant (mirroring `Reach.count()`) or move the prune call out of the per-tenant loop to run once per tick.
